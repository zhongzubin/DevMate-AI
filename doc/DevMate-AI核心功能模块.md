这个问题非常重要。因为我们不能只为了学习 RAG、Agent、MCP 等技术而做一个技术堆砌型项目。DevMate AI 必须先是一个有实际使用场景的软件产品，然后我们再通过它学习完整的 AI 应用工程技术。

我换一个角度，不从技术架构讲，而是从一个真实研发人员使用这个系统的过程讲清楚：它究竟能做什么、用户能看到什么、每个功能解决什么问题。

# 一、DevMate AI 最终是什么产品？

DevMate AI = 一个面向研发团队的 AI 工作助手。

假设你加入了一个新的软件项目。

你面对的是：

- 几十份项目技术文档。
- 几十个 API 接口。
- 一套数据库设计。
- 一堆开发规范和部署手册。

如果你想了解一个项目，可能需要翻阅大量文档，询问同事，或者自己阅读代码。

DevMate AI 希望把这些信息整合起来，让你通过一个对话界面就能查询、理解和处理研发相关任务。

## 功能 6：AI 质量评测与运行监控

这是我希望你特别重视的模块。

一个 AI 应用不能只看它能不能回答问题，还要知道：

- 回答到底准不准确？
- 检索出来的内容是否相关？
- 有没有产生幻觉？
- 模型响应时间是多少？
- 每次调用消耗多少 Token？
- 修改 Prompt 或 Chunking 后，效果有没有变好？

计划包含：

| -------- | -------------------------------- |
| 检索质量 | Recall@K、MRR、Context Precision |
| 生成质量 | Faithfulness、Answer Relevancy   |

例如：

我们准备 100 道固定问题，每次修改 RAG 检索参数、Prompt 或模型，都重新运行这些问题。

这会让 DevMate AI 不只是一个能运行的 Demo，而是一个具备质量验证能力的工程项目。

# 六、我想特别强调一个设计原则

我们不应该把 DevMate AI 做成一个简单的：

```
用户输入问题 → 调用 LLM → 返回答案
```

而应该逐渐演进为：

```
                用户请求
                   │
                   ▼
              意图与任务识别
                   │
          ┌────────┼────────┐
          ▼        ▼        ▼
        知识问答  数据查询  任务执行
          │        │        │
          ▼        ▼        ▼
         RAG      SQL/API   Agent
          │        │        │
          └────────┼────────┘
                   ▼
              结果整合与校验
                   │
                   ▼
                返回用户
                   │
                   ▼
                质量评测
```

这实际上涉及 AI 应用开发中非常重要的几个工程问题：

- 如何理解用户意图？
- 如何选择正确的数据源？
- 如何决定使用 RAG 还是 SQL？
- 如何控制模型调用工具？
- 如何校验模型输出？
- 如何保证数据权限？
- 如何评估整个系统的质量？

这些问题才是我们通过这个项目真正要掌握的东西。

我的建议是：第一版先把「文档管理 + RAG 知识问答 + 来源引用 + 无答案拒答」做扎实。 这条链路完成后，我们再逐步把它扩展成完整的研发协作助手。

下一步我们可以先把这六大模块进一步拆成详细的产品需求文档（PRD），明确每个页面的操作、输入、输出和业务规则，再开始写代码。
