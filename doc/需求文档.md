## 1. 文档效力

本文档定义 DevMate AI 的产品目标、范围、功能需求、业务规则和非功能要求，是需求确认基线。

- 本文档使用“必须”“应该”“可以”表达强制程度：必须为验收前提，应该为默认要求，可以为实现自由度。
- 功能编号 `FR-*`、业务规则编号 `BR-*` 是设计、测试和验收追踪的稳定标识。
- 优先级 `M` 表示 V0.3 MVP 必须交付，`T` 表示 V1.0 目标范围，`O` 表示后续候选能力。
- 技术实现边界、接口和数据模型以 `doc/详细设计文档.md` 为最高优先级技术标准。
- 验收证据和通过条件以 `doc/验收文档.md` 为准。
- `doc/DevMate总体架构方案.md` 与 `doc/DevMate-AI核心功能模块.md` 仅作为背景材料，不构成本文档的替代或补充规范。

## 2. 产品背景

研发团队的项目知识通常分散在技术文档、接口说明、数据库设计、部署手册、Bug 记录和任务系统中。开发者需要频繁切换工具、询问同事或人工翻阅资料，才能回答一个与项目相关的问题。

现有通用聊天模型无法直接解决这个问题：

- 模型不知道团队私有资料，容易编造答案。
- 把结构化统计问题交给文档检索会得到不可靠结果。
- 回答没有来源时，用户难以核对结论。
- 调用外部系统时，缺少可审计的工具边界。
- Prompt、检索或模型变化后，缺少回归评测依据。

DevMate AI 的目标不是构造一个“任意问题都能回答”的聊天框，而是建立一个来源可追踪、按数据源路由、能够持续评测的研发助手。

## 3. 产品定位与目标

### 3.1 产品定位

DevMate AI 是面向研发团队的统一自然语言入口，用于：

1. 检索项目技术资料并生成带来源的答案。
2. 管理团队知识库文档及其索引状态。
3. 查询任务、Bug 等项目结构化数据。
4. 通过受控工具完成有限、可审计的研发辅助任务。
5. 评估 RAG 与 Agent 的回答质量、延迟和调用成本。

### 3.2 产品目标

- **G-01 有依据问答**：回答必须基于检索证据或真实业务数据，并允许用户核对来源。
- **G-02 正确路由**：根据问题类型选择文档检索、结构化查询或工具流程，不能将所有问题都交给 RAG。
- **G-03 可交付 MVP**：先完成“文档管理 + RAG 问答 + 来源引用 + 无答案拒答”的闭合链路。
- **G-04 可持续演进**：核心模块保持清晰边界，能够从单轮问答演进到工具调用、Agent 和评测体系。
- **G-05 工程可验证**：关键路径具备自动化测试、日志、状态追踪和固定评测集。

### 3.3 非目标

- 首版不承诺理解任意代码仓库的调用关系。
- 首版不提供无人值守的代码修改、部署或生产数据写操作。
- 首版不实现复杂多租户、企业 SSO 和细粒度权限。
- 首版不以 Kubernetes、微服务拆分或复杂 Agent 编排为交付目标。

## 4. 用户与使用场景

### 4.1 目标用户

| 用户角色 | 主要诉求 |
| --- | --- |
| 研发工程师 | 快速查询架构、接口、配置、部署和历史问题 |
| 新加入项目的成员 | 通过自然语言理解项目技术栈、模块职责和关键流程 |
| 技术负责人 | 维护知识库、核对回答依据、分析研发数据 |
| 项目维护者 | 查看索引状态、运行评测、定位失败调用和配置问题 |

### 4.2 核心用户旅程

#### UJ-01 建立知识库

1. 用户进入知识库页面。
2. 上传 PDF、DOCX 或 Markdown 文档。
3. 系统校验文件并创建异步处理任务。
4. 页面展示“排队中、处理中、可用、失败”等明确状态。
5. 文档处理完成后可被问答检索。

#### UJ-02 提问并核对来源

1. 用户在智能助手页面输入项目问题。
2. 系统检索知识库并判断证据是否充分。
3. 证据充分时，系统给出答案和可定位的来源片段。
4. 用户展开来源，核对文档名称、片段和相关度。

#### UJ-03 证据不足时拒答

1. 用户询问知识库中不存在的信息。
2. 检索结果为空或低于最低证据阈值。
3. 系统明确说明当前资料不足，不生成看似确定的项目事实。
4. 若系统提供后续建议，建议不得伪装成已检索到的事实。

#### UJ-04 研发数据查询（目标范围）

1. 用户询问“当前有多少未解决的高优先级 Bug”。
2. 系统识别为结构化数据问题并选择受控查询工具。
3. 工具从真实业务数据源获取结果。
4. 系统基于查询结果生成统计说明，不将模型推算值当作真实数据。

## 5. 产品原则

- **证据优先**：知识问答必须有可追溯来源；没有证据时明确拒答。
- **数据源匹配**：文档问题走 RAG，结构化指标走查询服务，动作型任务走受控工具。
- **简单优先**：只有明确业务需求时才引入新的框架、队列或服务。
- **边界明确**：外部输入、文件解析、模型输出和工具参数必须校验；内部已受类型和契约保护的路径不重复防御。
- **失败可观察**：失败必须有稳定错误码、状态和日志，不通过静默兜底掩盖缺陷。
- **单用户可本地运行**：MVP 默认在本机运行，避免在核心闭环完成前引入复杂权限和部署设施。

## 6. 版本范围

### 6.1 版本路线

| 版本 | 目标 | 主要交付 |
| --- | --- | --- |
| V0.1 | 基础工程 | FastAPI、Vue 3、健康检查、前后端联调 |
| V0.2 | 文档入口 | 文档上传、列表、详情、删除、索引状态 |
| V0.3 | 首个可用 MVP | 文档解析、Embedding、Qdrant 检索、RAG 问答、来源引用、拒答 |
| V0.4 | 质量优化 | 混合检索、Reranker、Golden Set、回归评测 |
| V0.5 | 受控数据访问 | Bug/任务查询、SQL/API 工具、调用审计 |
| V0.6 | Agent 工作流 | 多步骤任务、状态管理、人工确认 |
| V1.0 | 完整展示 | 权限、监控、部署、评测面板和完整文档 |

### 6.2 MVP 边界

V0.3 MVP 必须包含：

- 单项目、单用户的本地运行模式。
- PDF、DOCX、Markdown 文件上传和管理。
- 文档解析、文本清洗、Chunk 切分、Embedding 和 Qdrant 索引。
- Top-K 向量检索和带来源的项目知识问答。
- 证据不足拒答和无效引用防护。
- 文档处理状态、失败原因和基本重试入口。
- 后端单元/集成测试，以及前端浏览器关键路径实测。

V0.3 MVP 不包含：

- 多项目管理、多租户、SSO 和复杂 RBAC。
- 混合检索、Reranker 和自动 Query Rewrite。
- 自然语言直接生成或执行任意 SQL。
- 自动修改代码、执行命令、部署或写入外部业务系统。
- 多 Agent 协作、MCP/A2A 和复杂工作流画布。
- 生产级高可用、Kubernetes 和跨地域部署。

## 7. 功能需求

### 7.1 基础平台

| 编号 | 优先级 | 需求 | 验收摘要 |
| --- | --- | --- | --- |
| FR-FND-001 | M | 系统必须提供前后端可启动的本地开发基线，并提供后端健康检查接口。 | 前端页面可访问，健康检查返回服务状态和版本。 |
| FR-FND-002 | M | 前后端必须通过 `/api/v1` 下的版本化 API 交互，并使用 Pydantic Schema 定义输入输出。 | API 文档可见，非法请求返回结构化错误。 |
| FR-FND-003 | M | 系统必须提供统一配置入口，LLM、Embedding、数据库和文件存储参数不得硬编码。 | 缺失必填配置时启动失败并给出明确提示。 |
| FR-FND-004 | T | 系统应提供统一的请求 ID、结构化日志和可追踪错误码。 | 一次请求可通过请求 ID 关联前后端日志。 |

### 7.2 文档管理

| 编号 | 优先级 | 需求 | 验收摘要 |
| --- | --- | --- | --- |
| FR-DOC-001 | M | 用户必须能够上传 PDF、DOCX、Markdown 文件；服务端必须校验扩展名、MIME 和文件大小。 | 支持格式成功进入处理流程，不支持格式被明确拒绝。 |
| FR-DOC-002 | M | 用户必须能够查看文档列表、文件名、大小、上传时间和当前处理状态。 | 上传后状态变化可在页面刷新后保持。 |
| FR-DOC-003 | M | 用户必须能够查看单个文档详情、处理错误和基础元数据。 | 成功和失败文档均能展示可理解的详情。 |
| FR-DOC-004 | M | 用户必须能够删除文档，系统必须同步清理 Chunk、向量和本地文件。 | 删除后文档不可检索，关联向量不存在残留。 |
| FR-DOC-005 | M | 同一项目内相同内容文件不得重复建立有效索引。 | 重复上传得到明确冲突响应或复用既有文档。 |
| FR-DOC-006 | M | 文档处理失败时必须保留失败状态和稳定错误码，并允许安全重试。 | 失败原因可见，重试不会创建重复有效向量。 |
| FR-DOC-007 | T | 用户应能够按项目、模块、类型和标签组织文档。 | 分类信息可在上传、列表和检索过滤中使用。 |
| FR-DOC-008 | T | 用户应能够更新文档并重新建立索引，旧版本在切换前仍可查询。 | 新版本成功后可检索，旧版本向量按设计清理。 |

### 7.3 文档处理与索引

| 编号 | 优先级 | 需求 | 验收摘要 |
| --- | --- | --- | --- |
| FR-ING-001 | M | 系统必须从 PDF、DOCX 和 Markdown 中提取可检索文本。 | 测试文档中的已知标题和正文能够被提取。 |
| FR-ING-002 | M | 系统必须清洗无效空白和解析噪声，并尽量保留页码、标题或章节等定位信息。 | 生成 Chunk 包含文档 ID、序号和可展示定位信息。 |
| FR-ING-003 | M | 系统必须按配置策略切分 Chunk，并记录顺序、内容和可追踪 ID。 | 长文档生成多个非空 Chunk，重叠策略可配置。 |
| FR-ING-004 | M | 系统必须通过 Embedding 适配器生成向量并写入 Qdrant。 | 成功文档对应向量数量与有效 Chunk 数量一致。 |
| FR-ING-005 | M | 索引构建必须具备幂等性，同一文档同一版本的重复执行不得产生重复有效向量。 | 重试后向量 ID 集合保持一致。 |
| FR-ING-006 | M | 文档状态必须遵循明确状态机，不允许无提示卡在处理中。 | 任务成功、失败或重试状态可追踪。 |

### 7.4 知识库问答

| 编号 | 优先级 | 需求 | 验收摘要 |
| --- | --- | --- | --- |
| FR-RAG-001 | M | 用户必须能够用自然语言向所选知识库提问。 | 有效问题返回回答、状态和来源列表。 |
| FR-RAG-002 | M | 系统必须先生成问题向量并执行 Top-K 检索，再构造回答上下文。 | 检索参数可配置，返回结果只包含当前项目数据。 |
| FR-RAG-003 | M | 有充分证据时，回答必须包含至少一个有效引用，引用能够映射到真实 Chunk 和文档。 | 回答中的每个引用 ID 均可在返回来源中找到。 |
| FR-RAG-004 | M | 无检索结果、证据低于阈值或模型判定证据不足时，系统必须拒答或明确说明信息不足。 | 无答案测试集不得生成无来源的项目事实。 |
| FR-RAG-005 | M | 系统必须校验模型返回的引用，不得向用户展示不存在的文档或 Chunk。 | 伪造引用被移除；无有效引用时转为拒答或生成失败。 |
| FR-RAG-006 | M | 回答界面必须展示来源文档名称、相关片段和可用的定位信息。 | 用户可展开来源并核对证据。 |
| FR-RAG-007 | M | 用户应能够限定检索到一个或多个文档。 | 限定范围外的文档不得出现在来源中。 |
| FR-RAG-008 | T | 系统应支持流式展示回答，同时保持引用和错误事件结构稳定。 | 首个内容和完成事件可被前端正确处理。 |

### 7.5 会话

| 编号 | 优先级 | 需求 | 验收摘要 |
| --- | --- | --- | --- |
| FR-CHAT-001 | M | 助手页面必须支持连续输入问题并展示当前会话中的问答记录。 | 刷新前的当前会话交互正常，失败问题不破坏后续提问。 |
| FR-CHAT-002 | T | 系统应持久化会话和历史消息，并确保用户只能访问自己的会话。 | 重新登录或刷新后可恢复历史会话。 |
| FR-CHAT-003 | T | 后续问题应能够引用当前会话上下文，但检索仍受项目范围约束。 | 上下文追问不会跨项目泄露来源。 |

### 7.6 项目分析与研发数据

| 编号 | 优先级 | 需求 | 验收摘要 |

| FR-DATA-003 | T | 系统必须统一“未解决”“高优先级”等业务指标定义，并在结果中说明口径。 | 同一指标查询使用一致定义。 |

| 编号 | 优先级 | 需求 | 验收摘要 |
| --- | --- | --- | --- |
| FR-TOOL-001 | T | 工具必须以显式名称、Schema、权限级别和超时执行。 | 非法参数在调用外部系统前被拒绝。 |

| FR-TOOL-003 | T | 系统必须记录工具调用参数摘要、结果状态和耗时，且不得记录敏感信息。 | 可从执行记录定位失败原因。 |
| FR-AGENT-001 | O | 系统可以在明确任务中编排多个受控工具，并保存中间状态。 | 步骤可恢复、可终止，关键动作可确认。 |

### 7.8 质量评测与运行观测

| 编号 | 优先级 | 需求 | 验收摘要 |
| --- | --- | --- | --- |
| FR-EVAL-001 | M | 项目必须维护最小 RAG 验收问集，覆盖可回答、无答案和引用定位场景。 | V0.3 至少包含 20 个固定用例。 |
| FR-EVAL-002 | T | 系统应记录检索结果、引用、模型、Token、延迟和错误信息。 | 每次问答可以定位所用模型和证据。 |
| FR-EVAL-003 | T | 项目应支持 Recall@K、MRR、引用有效率、拒答准确率和回答正确性回归。 | 修改检索或 Prompt 后可对比基线。 |
| FR-EVAL-004 | T | 系统应支持固定 Golden Set 和 LLM-as-Judge 辅助评测。 | 评测结果可重复运行并保存版本。 |
| FR-OPS-001 | T | 部署应提供 Docker Compose 本地编排和配置说明。 | 新环境可按文档启动核心服务。 |
| FR-OPS-002 | T | 系统应提供延迟、错误率、Token 使用和调用成本的基础统计。 | 监控页面或报告能够展示聚合结果。 |

## 8. 业务规则

| 编号 | 规则 |
| --- | --- |
| BR-001 | 知识库回答只能基于当前请求可访问的检索证据；不得将模型常识包装为项目事实。 |
| BR-002 | 每个事实性答案至少有一个有效引用；引用必须映射到真实文档和 Chunk。 |
| BR-003 | 证据不足时必须明确说明，不得用模糊措辞输出确定的项目结论。 |
| BR-004 | 结构化统计值必须来自业务查询结果；LLM 只能解释结果，不得自行生成或补全数值。 |
| BR-005 | MVP 默认单项目、单用户、本地可信环境；服务不得默认监听公网地址。 |
| BR-006 | 文档删除或替换必须同步处理向量数据，不能仅删除数据库记录或文件。 |
| BR-007 | 文档只有进入 `ready` 状态后才允许作为问答证据；失败或处理中文档不得被静默纳入检索。 |
| BR-008 | 文件类型、文件大小、检索范围和工具参数由服务端做最终校验；前端校验只用于交互提示。 |
| BR-009 | 具有外部副作用的工具必须声明权限和确认要求，并保留可审计记录。 |
| BR-010 | 系统不得记录完整密钥、认证信息或不必要的敏感文档内容。 |
| BR-011 | 模型输出属于不可信外部输入，必须经过结构和引用校验；校验失败应返回明确状态，不得静默编造降级结果。 |
| BR-012 | 防御措施应与真实风险匹配；不得在内部已受类型和契约保护的路径上重复实现无业务价值的兜底分支。 |

## 9. 页面与信息架构

| 页面 | 版本 | 主要能力 |
| --- | --- | --- |
| 智能助手 `/assistant` | MVP | 提问、回答、来源引用、拒答、当前会话记录 |
| 知识库管理 `/knowledge` | MVP | 上传、列表、详情、状态、删除、重试 |
| 项目分析 `/analysis` | 目标 | 技术栈、架构、模块和接口分析 |
| 研发数据 `/data` | 目标 | Bug、任务、项目和指标查询 |
| Agent 工作流 `/agent` | 后续 | 工具管理、任务执行、确认和记录 |
| 评测与监控 `/evaluation` | 后续 | Golden Set、质量、延迟、Token 和成本 |

页面必须提供加载、空数据、成功、失败和权限不足等与功能相关的状态。仅前端能够阻止的操作，不代表服务端已经保护。

## 10. 非功能需求

### 10.1 性能

| 编号 | 指标 |
| --- | --- |
| NFR-PERF-001 | 本地基线环境、1,000 个文档元数据和 100,000 个 Chunk 时，文档列表接口 P95 应不高于 500 ms。 |
| NFR-PERF-002 | 健康检查接口 P95 应不高于 300 ms。 |
| NFR-PERF-003 | 相同环境下，单次向量检索 P95 应不高于 1,000 ms。 |
| NFR-PERF-004 | 外部模型正常可用时，完整问答请求 P95 应不高于 60 s，并设置可配置超时。 |
| NFR-PERF-005 | 20 页以内、可解析 PDF 的本地索引任务应在 2 min 内完成；外部模型延迟和故障另作记录。 |

性能目标以详细设计定义的本地基线环境为准。无法达到时必须提供测量证据并确认调整，不能仅以主观体验替代。

### 10.2 可靠性与一致性

| 编号 | 要求 |
| --- | --- |
| NFR-REL-001 | 文档处理状态与索引结果必须一致；服务重启后不得无提示丢失已接受任务。 |
| NFR-REL-002 | 索引和删除操作失败时可重试，重试不得产生重复有效向量。 |
| NFR-REL-003 | PostgreSQL 和 Qdrant 不可用时必须返回明确错误，不应伪造成功结果。 |
| NFR-REL-004 | 模型调用超时或供应商错误必须可识别，前端能够重试当前问题。 |

### 10.3 安全与隐私

| 编号 | 要求 |
| --- | --- |
| NFR-SEC-001 | 密钥和连接信息只通过环境变量或本地未跟踪配置提供。 |
| NFR-SEC-002 | 上传文件必须限制类型、大小和安全存储路径，禁止路径穿越。 |
| NFR-SEC-003 | MVP 默认绑定 `127.0.0.1`，对外暴露前必须补充认证和网络边界说明。 |
| NFR-SEC-004 | 日志默认不得记录完整 Prompt、完整文档内容、密钥、Token 或个人敏感信息。 |
| NFR-SEC-005 | 工具必须遵循最小权限，不允许模型直接拼接执行任意 SQL、Shell 或文件路径。 |
| NFR-SEC-006 | 检索必须按项目范围过滤，禁止跨项目返回来源。 |

### 10.4 可维护性与可测试性

| 编号 | 要求 |
| --- | --- |
| NFR-MNT-001 | 后端业务逻辑与框架、数据库、向量库和模型供应商解耦，核心流程可通过替换适配器测试。 |
| NFR-MNT-002 | API、配置、数据模型和错误码必须有单一权威定义，避免前后端重复维护。 |
| NFR-MNT-003 | 新功能和缺陷修复必须包含相应自动化测试；外部模型默认使用测试替身。 |
| NFR-MNT-004 | 前端页面关键路径必须通过真实浏览器验证。 |
| NFR-MNT-005 | 代码不得引入无明确需求的抽象、框架或防御分支。 |

## 11. 数据与内容约束

| 编号 | 约束 |
| --- | --- |
| DC-001 | MVP 支持 `.pdf`、`.docx`、`.md`；默认单文件上限 20 MiB，可通过配置调整。 |
| DC-002 | 文件按项目隔离；MVP 使用一个默认项目，但数据模型保留 `project_id`。 |
| DC-003 | 文档内容哈希用于项目内重复检测。 |
| DC-004 | Chunk 必须可追溯至文档、版本和顺序，向量载荷不得只保存裸文本。 |
| DC-005 | 结构化业务数据必须使用脱敏演示数据或明确授权的数据源。 |
| DC-006 | Golden Set 和测试资料不得包含真实密钥、个人隐私或受限制的内部信息。 |
| DC-007 | 扫描版 PDF 首版可不保证 OCR；无法提取文本时必须进入明确失败状态。 |

## 12. 假设与约束

- 目标部署以 Windows 本地开发环境为起点，同时保持 Linux 容器兼容能力。
- 后端使用 Python 3.12 或更高版本、uv、FastAPI 和 pytest。
- 前端使用 Vue 3、TypeScript、Vite 和 npm。
- PostgreSQL 用于业务元数据，Qdrant 用于向量数据，二者均通过 Docker Compose 或本地服务提供。
- LLM 与 Embedding 供应商通过适配器接入，具体模型由配置决定，不在产品需求中写死。
- 当前仓库尚未实现应用代码，本文件描述的是已确认目标基线；存在代码后，若实现与文档冲突，按 `AGENTS.md` 的文档治理规则处理。

## 13. 成功指标

V0.3 MVP 成功标准：

- 用户可完成“上传文档 -> 等待可用 -> 提问 -> 查看来源 -> 核对答案”的完整流程。
- 固定验收问集中，可回答问题的答案包含正确事实和有效引用。
- 无答案问题不会被包装为确定事实。
- 删除文档后，其 Chunk 和向量不可再被检索。
- 后端相关测试全部通过，前端关键路径完成浏览器实测。

V1.0 成功标准：

- 能在同一入口区分知识问答、研发数据查询和受控任务执行。
- 关键调用具备可观测性和可回归评测。
- 新环境可按部署文档启动并完成演示流程。

## 14. 需求追踪与变更

- 详细设计必须引用 `FR-*`、`BR-*` 和 `NFR-*` 编号，说明实现位置。
- 验收文档必须引用需求编号，并给出可执行用例和证据要求。
- 新增或修改需求时，必须同步检查详细设计、验收阈值、测试计划和版本范围。
- 未经验收的能力只能标记为“已规划”或“实现中”，不得在产品说明中标记为“已实现”。
