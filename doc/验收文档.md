## 1. 文档效力

本文档定义 DevMate AI 的验收条件、测试用例、质量阈值和证据要求。

- 验收必须同时对照需求文档和详细设计文档。
- 本文档中的“通过”必须由可复现命令、测试结果、日志、截图或人工记录支持。
- 当前仓库尚无应用代码，本版本是验收基线，不代表任何验收项已经通过。
- 未执行项必须标记“未执行”及原因，不得以设计合理性替代运行结果。

## 2. 验收原则

- **需求可追踪**：每个关键用例引用需求或业务规则编号。
- **结果可复现**：记录环境、命令、输入、预期结果和实际结果。
- **后端自动验证**：业务逻辑和 API 优先使用 pytest。
- **前端真实操作**：关键用户路径使用浏览器实测。
- **证据可核对**：RAG 回答必须检查来源和原文，不只检查语言是否流畅。
- **失败不伪造**：外部依赖失败时验证明确错误和重试，不要求制造表面成功。

### 9.1 RAG 固定问集

V0.3 至少 20 个用例：

- 12 个可回答问题，覆盖至少 3 份文档。
- 6 个无答案问题。
- 2 个引用定位或文档过滤问题。

每项必须记录：

- 问题。
- 预期事实点。
- 预期文档和 Chunk 或可接受来源范围。
- 是否必须引用。
- 实际回答、引用和结论。

### 9.2 V0.3 质量阈值

| 指标 | 通过阈值 |
| --- | --- |
| 检索 Hit@5 | ≥ 85% |
| 引用有效率 | 100% |
| 可回答问题的必需事实覆盖率 | ≥ 80% |
| 无答案问题拒答准确率 | ≥ 90% |
| 跨项目来源泄露 | 0 例 |
| 伪造文档/Chunk 引用 | 0 例 |

未达到阈值的用例必须作为缺陷处理。若因测试集本身设计不合理需要调整，必须记录调整理由并重新确认，不得通过删除失败用例“通过”验收。

V0.4 应扩展到 50 至 100 个 Golden Set 用例，并增加 Recall@K、MRR、Context Precision、Faithfulness 和 Answer Relevancy 报告。

## 11. 数据一致性验收

可使用只读 SQL 和 Qdrant 查询核对：

```text
documents.chunk_count == document_chunks 有效数量
document_chunks qdrant_point_id 集合 == Qdrant document_id 过滤后的有效点集合
删除成功文档后，两个集合均无有效的本项目点位
```

必须验证：

- 索引重试后无重复有效点。
- 文档失败时不出现 `ready` 状态。
- 删除失败时不显示“删除成功”。
- 服务重启后状态仍可恢复或明确失败。
- 相同内容文档未重复建立有效索引。

## 15. 回归策略

每次合并前至少运行：

1. 后端相关单元、API 和集成测试。
2. 前端类型检查、相关组件测试和构建。
3. 受影响页面的浏览器实测。
4. 修改 RAG 配置、Prompt、Embedding 模型、Chunk 策略或检索逻辑时运行固定问集。
5. 修改数据库或向量结构时执行迁移和一致性检查。

回归失败时：

- 阻断与失败路径直接相关的合并。
- 记录失败用例、复现步骤和日志。
- 修复后重跑失败用例和相关回归集。
- 不以其他用例通过抵消阻断项失败。

## 16. 阻断性缺陷

以下问题一律阻断 V0.3 验收：

- 文档上传成功但状态永久卡住且无恢复路径。
- 文档未 `ready` 却参与检索。
- 知识库无证据时生成确定项目事实。
- 回答引用不存在或无法定位到真实 Chunk。
- 跨项目返回来源。
- 删除文档后仍能检索到其内容。
- 外部依赖不可用时伪装为成功。
- 密钥或敏感数据出现在响应、日志或 Git diff。
- 后端测试失败。
- 需要浏览器实测的前端主流程未执行或失败。

非阻断项必须明确记录风险、责任和后续计划，不能只写“后续优化”。

## 17. 完成定义

满足以下全部条件才可通知验收：

- V0.3 需求和详细设计已实现，范围与确认方案一致。
- API、数据模型和状态机符合详细设计。
- 新增/修改功能有对应 pytest 测试，结果全部通过。
- RAG 固定问集达到本文件阈值。
- 文档与向量一致性检查通过。
- 前端关键路径完成真实浏览器实测。
- 安全、敏感信息和未跟踪产物检查通过。
- 未执行项及原因已记录，阻断项为 0。
